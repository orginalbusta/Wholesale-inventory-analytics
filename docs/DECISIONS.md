# Decisions and deviations log

Record any decision that deviates from the specs in `docs/`, or that a reviewer might question. Newest first.

| Date | Decision | Why | Alternatives considered |
|---|---|---|---|
| 2026-10-14 | **Medium scale cut to ~40k orders / ~300k order lines** (from ~120k / 850k-1M); still 650 customers, 1,200 SKUs, 60 suppliers, 36 months. Decided by Harsh | The original volumes implied ~$53M/yr of synthetic revenue, implausible for a ~20-person distributor and easy to misread as a claim about the real company. Now ~$17M/yr (~1,100 orders/month, ~7 lines/order). Small scale (~$8M/yr) unchanged | Keep spec volumes; lower prices instead (would distort unit economics) |
| 2026-10-14 | **One committed FX file for generator and dbt.** `transform/seeds/fx_static_rates.csv` (built by `scripts/build_fx_seed.py`) holds monthly units-per-USD for all 7 currencies: FRED monthly means for INR/BRL/CNY/MXN (the 4 FX series plus RSXFS and UMCSENT were verified live), labeled approximations for MGA/MAD, forward-filled past the last FRED month. The generator prices `unit_cost_local` from it and dbt converts back with it. The FRED API load stays for context and future forecast regressors | The spec had the generator use the FRED cache when a key exists and the seed otherwise, so output would depend on whether a key was set (CI has none), breaking "same seed = identical output". Monthly rates are how a small distributor would book PO costs anyway | Daily FRED rates in both layers (non-deterministic without a key); generator-only FX (USD costs wouldn't reconcile in dbt) |
| 2026-10-14 | Added an ERP **`product_price_history`** table (price-change log) | dbt snapshots only see changes from the first pipeline run, so 18-36 months of backfilled cost changes would be invisible and margin couldn't use cost as of order date. Real ERPs keep this log. `snap_products` still captures changes delivered by `simulate-day` | Backfill as one load per day (slow, artificial); use current cost for all history (wrong margins) |
| 2026-10-14 | `simulate-day` re-runs the whole simulation to the new day instead of restoring a pickled state; `_state.json` only records the as-of date and runs. Every day draws from its own seeded random stream, so earlier days replay identically (tested) | Far simpler and less fragile than serializing inventory, open POs, pending returns, price queues and RNG state. Cost: a full re-run per day (small 1.4s, medium ~5s) | Serialize full state (more code, easy to get subtly wrong) |
| 2026-10-14 | `_extracted_at` is a simulated timestamp (02:00 after the extraction day), not the wall clock | Byte-identical output. Consequence for Phase 3: the backfill ends 2026-09-30, so `dbt source freshness` against today's clock will call it stale; judge freshness relative to the simulation, or rely on the nightly simulate-day to keep it current | Wall-clock extraction time (breaks determinism) |
| 2026-10-14 | Demand is realized **order-first**: customers place orders at Gamma-distributed rates scaled by the day's demand index; each order picks SKUs with probability proportional to revenue weight x trend x seasonality x show x lifecycle x price effect x customer-type affinity; quantities are negative-binomial case packs. Expected units per SKU-day still follow the spec's multiplicative formula (`_truth/expected_demand_daily.parquet`) | The spec's "per-SKU negative binomial, then group into orders" is hard to do without breaking either per-SKU demand or realistic baskets. Order-first gives realistic baskets, churn effects and lumpy demand together | SKU-first draws then bin-packing into orders |
| 2026-10-14 | `pareto_alpha` replaced by `top20_revenue_share` (0.79): the Zipf exponent is solved per scale, and each SKU's choice weight divides out its price and typical line size so expected revenue follows the target. Realized top-20% share: 75.0% (small), 80.5% (medium) | A Pareto shape parameter doesn't map predictably to "top 20% of SKUs = 75-80% of revenue" at both 200 and 1,200 SKUs; solving for the share does | Hand-tune alpha per scale |
| 2026-10-14 | `gem_show` share of orders is ~8% (small) / ~12% (medium), not the spec's 20% | Shows cover ~6% of days. 20% of orders would need ~6x order volume on show days, contradicting the spec's 2.5-4x show multiplier. Kept the multiplier, since it drives the purchasing and dead-stock story | 6x show multiplier (unrealistic spikes) |
| 2026-10-14 | Order and line discounts are stored in **percentage points** (5.0 = 5%) | Matches the `*_pct` column names; staging divides by 100 | Fractions |
| 2026-10-14 | An order whose lines all go unfilled (stockout) gets status `cancelled`; its lines keep `quantity` with `quantity_fulfilled = 0`. **Phase 4 note:** true demand in `int_sku_demand__daily` must count ordered quantity on cancelled orders too, or stockout demand is lost | Nothing ships, so "shipped" would be wrong. Customer-initiated cancellations (3%) look the same in raw data: a realistic ambiguity to document in the model | Leave status `placed` forever |
| 2026-10-14 | Products are created in the ERP 180 days before launch, and cost changes only apply after creation. Supplier `min_order_value_usd` is an attribute only (the naive buyer ignores it) | The buyer places the first PO before launch (quoted lead times reach ~110 days), and a PO can't reference a product that doesn't exist yet (a test caught this). Enforcing MOVs would add complexity without improving the story |  |
| 2026-10-14 | **Warehouse strategy confirmed with Harsh: DuckDB builds the public site; Snowflake is the cloud showcase target.** The GitHub Pages dashboard and dbt docs are rebuilt from DuckDB in GitHub Actions (free), including a nightly scheduled `simulate-day → load → dbt build → deploy` so the live site visibly refreshes. The same dbt project runs on Snowflake (`--target snowflake`) for README screenshots, build times and credit usage (Phase 8) | Harsh wants a public link that demonstrates the system working without ongoing cost. The static site never queries a warehouse, so it stays up for free; making it depend on Snowflake would freeze or break rebuilds when the 30-day trial ends. Running one dbt codebase on both adapters is a stronger signal than either alone | Snowflake-only (CI + deploy spend credits on every PR/merge; site stops refreshing after the trial; reviewers can't clone and run) |
